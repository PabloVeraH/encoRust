## Why

`docs/mp3-encoder/14-roadmap-and-milestones.md` currently tracks milestone
status (M0-M9) as hand-written prose — a row like "M0 ✅ Verified: `cargo
build`... all pass" is only as trustworthy as whichever LLM session last
edited it. Across many sessions and multiple LLMs working on this
solo-owned project, that self-attestation is exactly the failure mode the
project's own `00-overview.md` §4.1 already warns about for numeric
tables ("never let an LLM hallucinate a table and ship it untested") —
the same risk applies to *progress claims*, not just DSP constants. A
milestone marked done that silently regressed after a later change (or
was never actually verified) is invisible until someone reads the source.

We need a milestone-closure record that is **generated by actually
executing** each milestone's Definition-of-Done checks — never
hand-authored by an LLM — and anchored to the exact commit it was run
against, so any future session (human or LLM) can trust "M3: PASS"
without re-reading or re-verifying the whole project.

## What Changes

- Add a per-milestone **check manifest** declaring, machine-readably,
  which commands constitute that milestone's Definition of Done (test
  filters, whether clippy/fmt gate it, whether external-decoder checks
  apply from M8 onward).
- Add a **verification script** that reads the manifest for a given
  milestone, executes the declared checks for real, and is the **only**
  writer of ledger entries — an LLM narrating a result in prose is never
  an acceptable substitute for running it.
- Add an **NDJSON ledger** (append-only) as the source of truth for
  milestone verification history: one record per run, capturing
  pass/fail, a short summary, a hash of full output, and the exact git
  commit the run was performed against.
- Add a generated **human-readable summary** derived from the ledger
  (not hand-maintained) that a cold-start LLM session reads first to
  learn current, evidence-backed progress without executing anything or
  reading prior session transcripts.
- Update `docs/mp3-encoder/14-roadmap-and-milestones.md`'s status table
  to point at (or be regenerated from) the ledger's latest record per
  milestone, instead of hand-written pass/fail prose.
- Add explicit instructions (in the roadmap doc and/or project
  `CLAUDE.md`) directing any LLM working on this project to invoke the
  verification script to close a milestone, and never to hand-edit the
  ledger or the generated summary.
- Enforcement for now is **convention, not a blocking hook** — this is a
  solo-owned project at this stage; a harness-enforced gate (e.g. a
  Claude Code `Stop` hook refusing to end a session claiming milestone
  completion without a matching fresh ledger PASS) is an explicit
  candidate for later, not part of this change.

## Capabilities

Pure tooling/process addition internal to how this project tracks its
own build progress — it does not change any `mp3-core`/`mp3-cli`/
`mp3-wasm` product behavior or public API. `skip_specs: true` is set in
this change's `.openspec.yaml` accordingly; see `design.md` for the
mechanism (ledger schema, script behavior, manifest format).

## Impact

- **New files**: a check-manifest file, a verification script (location
  and language — shell vs. a small Rust `xtask` — decided in
  `design.md`), an NDJSON ledger file, a generator for the human-readable
  summary.
- **Modified files**: `docs/mp3-encoder/14-roadmap-and-milestones.md`
  (status table becomes ledger-derived), likely the project's
  `CLAUDE.md`/agent instructions (mandate invoking the script).
  `.gitignore` is unaffected in intent — the ledger and its generated
  summary are working-progress artifacts for this solo project, tracked
  the same way `docs/` already is (kept local for now, per the earlier
  deliberate decision not to publish the development plan).
- **No impact** on `crates/mp3-core`, `mp3-cli`, or `mp3-wasm` source, or
  on the encoder's eventual public API.
